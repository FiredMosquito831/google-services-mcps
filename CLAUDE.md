# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

google-services-mcps is a set of MCP servers for Google products, packaged as Claude Code plugins in one marketplace, with an installer (`gsm`) for Codex, OpenCode and Antigravity (`agy`). One plugin per product (23 in total), and each plugin runs one MCP server with the same name as the plugin. Public repository: https://github.com/FiredMosquito831/google-services-mcps (owner FiredMosquito831). Licence Apache-2.0 with NOTICE. The website is GitHub Pages from `site/`.

Status: built and tested offline (1163 tests on Windows: 1160 pass, 3 skipped, 2026-10-31; the release workflow runs the suite on Linux, 1123 tests with 0 failures for v1.26.0), smoke test over all servers, plugin validation. The npm package is `google-services-mcps`, one package. 1.26.0 is the latest release under that name (npm `latest` and GitHub release v1.26.0, checked 2026-10-30; v1.24.4 carried 1.2.0–1.24.4 and v1.26.0 carried 1.24.5–1.26.0). 1.26.1 is merged on main and not released yet. The scoped name `@firedmosquito831/google-services-mcps` is deprecated (all five versions, 2026-10-16). The owner ran `npm deprecate` in a terminal, because it needs a one-time password. The `npm` workflow publishes the package when a GitHub release is published (trusted publishing, with provenance). Live checks so far, on the owner's accounts: gcloud with an application-default login on a danubelabs.net Google account (readiness check and enabling APIs); gsc reads, and `health` with `live: true` found the login valid (2026-10-29); gmail reads (2026-10-29: the profile on six accounts, personal @gmail.com ones included, and search, labels and a full message on one; the danubelabs.net account's login was refused). The other servers have not run against live Google accounts, and no mail has been sent. Treat any other live claim as unverified until a live test has run.

## Commands

Run from the repository root.

- `npx tsc --noEmit`: typecheck.
- `npx tsc -p tsconfig.json`: compile to `dist/`. Tests import from `dist/`, so compile before running a single test file.
- `npm run build`: bundle the 23 plugins and the root `gsm.mjs` (`scripts/bundle.mjs`). Rewrites `plugins/**`.
- `npm test`: compile, then `node --test tests/*.test.mjs`.
- One test file: `npx tsc -p tsconfig.json` then `node --test tests/gate.test.mjs`.
- `node scripts/smoke.mjs`: starts every bundled server over stdio (needs a build).
- `claude plugin validate .` and `claude plugin validate plugins/<id>`: manifest checks.
- Generators (never hand-edit their output): `npm run surfaces` (`docs/SURFACES.md`), `node scripts/gen-capabilities.mjs` (`docs/CAPABILITIES.md`, `docs/capabilities/`; each API with the link to Google's documentation from the catalog's `documentationLink`, the API's documentation home, as there is no reliable per-method link), `node scripts/gen-readme.mjs --check` (README products block), `node scripts/gen-site.mjs` (site product section, sitemap), `node scripts/gen-servers.mjs` (`config/servers.json` from `config/products.json`), `node scripts/build-catalog.mjs` (`data/catalog.json`), `node scripts/snapshot-discovery.mjs` (`data/discovery/`, `data/scopes.json`, and `data/discovery/_revisions.json`: each snapshot's Discovery `revision` and fetch time in UTC; snapshots older than this record say `unknown (snapshot 2026-10-15)`), `node scripts/gen-service-account-scopes.mjs` (`src/core/service-account-scopes.ts`; needs a compiled dist/, `--check` writes nothing). `gen-readme.mjs`, `gen-capabilities.mjs` and `gen-surfaces.mjs` take `--check` (writes nothing, exit 1 when stale); `tests/docs-drift.test.mjs` runs all three, so stale generated docs fail `npm test`.
- `node scripts/check-discovery-freshness.mjs [--json]`: report-only check of the Discovery data against Google's public documents (no key, no sign-in) for every API version in config/servers.json and data/catalog.json, plus the preferred directory, in the snapshot's URL order with one retry. On 2026-10-30 that was 844 GETs in under two minutes: 305 of the 536 documents answer 404 at the documented path and are served by the API's own host. Reports revisions (now vs recorded), methods added, removed or changed by id (against the snapshot, else the catalog), preferred versions changed since the catalog, directory APIs the catalog lacks (`unassigned` ones shown with their reason), and documents not checked (needs a key, gone, failed). Exit 0 no differences, 1 differences, 2 incomplete or a usage error; a newer revision with the same methods is not a difference. It writes nothing. Refreshing the snapshots changes the tools, so it is a separate decision. `tests/discovery-freshness.test.mjs` runs it and the snapshot against a fake Google on 127.0.0.1 (`--root`, `--origin`, test-only; scripts/discovery-urls.mjs).
- `tests/curated-contract.test.mjs`: every curated tool (149) runs with the HTTP layer stubbed, and each request is checked against `data/discovery` (method, verb, path template, query parameters, body fields, deprecated flags). A new curated tool needs a row there, or a reason in its SKIPPED list.
- `npm run pack:check` or `npm publish --dry-run --access public --ignore-scripts`: what would be published. Without `--ignore-scripts`, `prepublishOnly` runs the build and tests.
- Bump: `node scripts/bump.mjs patch|minor|major` (or `X.Y.Z`) moves `package.json` and `package-lock.json` together. Release: publish a GitHub release `vX.Y.Z` (not a draft) after the bump is on main. `.github/workflows/npm.yml` checks the tag against `package.json` and publishes the package. Nothing publishes on a push.
- Installer, always with a temp home in tests: `node gsm.mjs install --agent <claude|codex|opencode|agy|all> --plugin <id,...>|all [--scope global|project|local] [--path <dir>] [--dry-run] [--home <dir>]`, and `node gsm.mjs uninstall ...` or `uninstall --all --yes`, `node gsm.mjs list`.
- For Claude Code tests, set `CLAUDE_CONFIG_DIR` to a fresh temp folder. This isolates Claude's own state (verified).

## Architecture (big picture)

Four layers, and the generated plugin folders are the join point.

1. **Product map** (`config/products.json`, the source of truth). Each product has a group, a server name (equal to its id), a curated module or none, a list of generated APIs (per-method tools, capped at 350 tools per server) and a list of gateway APIs. `config/servers.json` is generated from it.
2. **Tool generation.** Curated tools are hand-written in `src/servers/*.ts` (each exports `buildTools(cfg)`). Generated per-method tools come from Google's Discovery documents (`src/core/discovery/`, snapshots in `data/discovery/`). Gateway tools (`api_search`, `api_describe`, `api_call`, in `src/core/gateway.ts`) reach every other API of the product through the catalog (`data/catalog.json`, 541 entries and 31,633 methods, rebuilt 2026-10-30 in 1.26.0). `scripts/bundle.mjs` merges curated, generated and gateway tools into one entry per server.
3. **Runtime** (`plugins/<id>/`, generated). `servers/<id>.mjs` is the MCP server. `hooks/hooks.json` runs `bin/gsm-hook.mjs` before each call to the plugin's tools. `tool-map.json` and `method-kinds.json` tell the hook the safety class of each tool and method. `.mcp.json` passes plugin options (allow_writes, confirmation, toolset, token_dir) to the server as env vars.
4. **Installer** (`src/cli/`, bundled into `gsm.mjs` at the root and into each plugin's `bin/`). Installs into Claude Code via the `claude plugin` CLI, and into Codex, OpenCode and agy by writing their config files. Each install copies the product's files to `<home>/.google-services-mcps/runtime/<product>/` and points the agent config there.

**Consent and safety flow.** Reads never prompt. Write and destructive tools are only listed when `GSM_ALLOW_WRITES=true`. Writes prompt through the hook. Destructive tools prompt twice: the hook, then an MCP elicitation with an exact preview from `ctx.gate()` (`src/core/approval.ts`). A tool whose exact effect takes reads to show defines `prepare` (`ToolDef` in `src/core/tools.ts`; today `gmail_send`, `gmail_reply` and `gmail_trash`): runServer runs it with the call's account, gives its `preview` to the gate in place of the raw arguments, and passes the prepared action to the handler, so what runs is what was approved. Clients with neither hooks nor elicitation fail closed. Policy rules (`policy.json` in the token directory) allow, ask or deny by tool or method. Audit lines hold a hash of the arguments, never the values. The model cannot bypass any of this: there is no model-controlled `confirm` argument, and it must not be reintroduced.

**Scopes.** Logins request a profile (`readonly` default, `readwrite`, `full`, or an explicit list). Tools the stored token cannot use are not registered. Logins merge with the stored scopes of the account named with `--account` (`auth_login`'s `account`), keeping only scopes a server of the group uses; with no account nothing is merged; `--replace` drops them. Gateway methods count toward login coverage too (`src/core/scopes.ts`, `src/core/registry.ts`). A product can declare a `scopePolicy` in `config/products.json` (copied into `config/servers.json` and each plugin's servers.json): `onlyIn` limits a scope to some profiles (an empty list: none), and `optional` names parts (APIs) left out of every profile unless the login names them (`--with`, `auth_login` `with`). Only gmail has one: `https://mail.google.com/` only in `full`, `gmail.settings.sharing` in none, `postmaster` optional. The policy changes only what a login asks for; tool kinds, the gate and the startup scope check are unchanged. A product can also declare `scopeOverrides` (per generated API, the scopes a method declares when its Discovery document lists none); only gbusiness has them (`business.manage`, 1.24.1). Unlike a policy, an override changes the tools' declared scopes, so it changes both the login and which tools register. A listed toolset can declare `preferScopes` (per profile, `readonly` or `readwrite`; copied as `toolsetScopes`): its login takes those scopes first, then the greedy rule (1.25.0; the `prefer` field of a requirement, `preferFields` in src/core/scopes.ts). Seven `google` lists have one (gcalendar, gchat, gcontacts, gtasks, gclassroom, gadmin, gtm, readwrite only). A preferred scope is allowed only where Google's scope documentation gives each tool it covers the same reach as the scope it replaces (owner's rule, 2026-10-30); when unsure, keep the broad scope. gen-servers and bundle refuse a preferred scope no tool of the toolset accepts.

**Shared rules that live in two places.** `src/core/discovery/methods.ts` (`classifyMethod`) and `src/cli/method-kinds.ts` (a copy, used by the plugin bundles) must agree. `tests/cli-surface.test.mjs` checks every catalog method.

## Rules (repository-specific)

- Versioning: a commit on `main` that changes a production file bumps the version in the same commit, with `node scripts/bump.mjs patch|minor|major`. Production files: `src/**`, `config/**`, `scripts/bundle.mjs`, `scripts/install.*`, and `package.json` (name, bin, files, dependencies). Tests, docs, `site/`, README, this file and `.github/**` need no bump on their own. A commit that mixes both still bumps.
- Semver: PATCH for fixes, refactors with no visible change, dependency updates and install fixes. MINOR for new commands, options, tools, products or behaviour. MAJOR for breaking changes: removed or renamed commands, options, environment variables or config keys, or anything users must act on. When unsure between PATCH and MINOR, pick PATCH for a fix and MINOR for new capability.
- Release, in order: (1) the bump (`node scripts/bump.mjs`) and the `CHANGELOG.md` entry for the version go in the same commit as the change; (2) push to `main` with the owner's go-ahead; (3) publish a GitHub release `vX.Y.Z` (not a draft) on that commit, with the changelog entry as its notes. The release starts the npm publish. A push does not. Plugin manifests keep `MANIFEST_VERSION` in `scripts/bundle.mjs` and change only when plugin content changes. Check afterwards: the publish run passed, the log shows `+ google-services-mcps@X.Y.Z`, and the registry's `latest` is X.Y.Z.
- Keep this file current. When the stack, a command, a rule, a preference or a non-obvious fact changes, update the matching section in the same change. Correct a stale line rather than adding a contradiction.
- Do not hand-edit generated output: `plugins/**`, `gsm.mjs`, `dist/`, `build/`, `config/servers.json`, `docs/SURFACES.md`, `docs/CAPABILITIES.md`, `docs/capabilities/`, the README products block, the site product section, `src/core/service-account-scopes.ts` (scripts/gen-service-account-scopes.mjs). Change the source (`config/products.json`, `src/**`, `scripts/**`) and regenerate.
- Tool names must fit 64 characters including the prefix `mcp__plugin_<plugin>_<server>__`. Budget = 49 minus the lengths of the plugin id and the server name. Keep plugin ids short; the generator enforces the budget for generated names.
- Writes and destructive actions go through `ctx.gate()`. Never call a Google API that changes state from a path that skips the gate.
- `prepare` on a curated tool (src/core/tools.ts) only works out the action and its preview: reads only, never a change. runServer runs prepare, then the gate with `prepared.preview`, then the handler with the prepared action; the gate is never skipped, and a handler called without `prepared` (the contract test) works the action out itself. tests/gmail-send-gate.test.mjs drives this through a real runServer child.
- Gmail sending (src/servers/gmail.ts, src/servers/gmail-mime.ts): messages are 7-bit ASCII RFC 5322 MIME built by `buildMime`; up to 5 MB in the JSON `raw` field, above that through the upload endpoint (googleapis `media`, `uploadType=multipart`); over 35 MB refused before any file is read. Attachments are full paths, and files in the token folder, gcloud's folder or a key file named by `GOOGLE_APPLICATION_CREDENTIALS` / `GSM_SERVICE_ACCOUNT_KEY_FILE` are refused. A reply sets `threadId`, `In-Reply-To` and `References` from the original. Send and reply are destructive, as `classifyMethod` classifies `messages.send`; no scope beyond the 1.2.0 Gmail policy.
- Gmail parity tools (1.7.0): each description names the Google tool it matches, and gmail's `toolsets.google` lists them with `matches` (a tool with no match needs a note; gen-servers enforces it). `gmail_label` refuses adding TRASH or SPAM and `gmail_unlabel` refuses removing TRASH (they point to `gmail_trash` / `gmail_untrash`); kinds follow `classifyMethod` (`modify` and `untrash` write, `trash` destructive). `gmail_list_labels` returns the plain array unless `page_size` or `page_token` is given, so a 1.6.0 caller gets the same answer.
- Anything that reads a method's kind must use `classifyMethod`. A POST counts as a read only for the narrow verb list and exact names in `src/core/discovery/methods.ts`. Credential names (token, credential, secret, password, authorization, key) are always writes.
- Scopes merge by default, per account. A login merges the stored scopes of the account it names (`--account`, `auth_login` `account`, sent to Google as `login_hint`) and only those a server of the group uses (`groupScopeUniverse` in src/cli/scopes.ts; a plugin reads its group's list from `groupScopes` in its servers.json, written by the bundle). Never merge another account's scopes (the default account's, say) into a login, and never send `include_granted_scopes`. A save never takes usable scopes away from an account unless that account was named and signed in, or the user passes `--replace`; otherwise the login saves nothing and says how to retry (src/cli/login.ts).
- Scope rules for one product are data (`scopePolicy` in config/products.json, read through `policyFields` in src/core/scopes.ts), never a branch on a product name. Without a policy a requirement gets no policy fields and resolves exactly as before; tests/gmail-scopes.test.mjs checks that for every other server. The ADC sign-in (`adcScopesFor` in src/core/tools.ts) applies the same policy.
- Credentials: only `gsm status --check`, `gsm doctor` and the health tool with `live: true` ask Google about a stored login (src/core/grant-check.ts). A read tool never does. Logout and `account_remove` revoke only when no other group here has the same account (`otherGroupsWithAccount` in src/core/accounts.ts, from accounts.json and file names, never a token): Google's revocation removes every grant the account gave the project, for all its clients. `gsm logout --revoke-all` revokes anyway. A refused login's message names Google's `error` and `error_subtype`, tells a reauthentication (`invalid_rapt`) apart, and points to `auth_login` first, the terminal second. Logout revokes the grant first (`--local-only` skips that). Every message about a login is redacted with the token and the client secret before it is shown.
- Pre-login: the OAuth groups (workspace-user, searchconsole, business, developer) register only tools that need no scope, plus `auth_status`, until a login exists: an account of the group, or the ADC login (src/core/tools.ts, `loginSourceOf` in src/core/auth.ts). The apikey group has its own key.
- ADC is a sign-in option for every OAuth group (src/core/adc.ts). `auth_login` without `method` returns the two options with their pros and cons, and the person chooses. Tests that start a sign-in pass `method`. The suite reads the ADC file's type, quota project and a SHA-256 of its refresh token. It never returns, prints or writes the token, and never writes to the ADC file. `adc.scopes.json` in the token folder records the group, scopes and hash of the last ADC login the suite made. A group uses ADC only when none of its accounts is signed in here (`adcSourceFor`). A group on ADC gets its scopes from the record, and a record whose hash no longer matches the file is ignored.
- Curated tools that return a secret are writes, as their generated copies are. config/tool-kinds.json holds the kind of every Discovery method that is not a plain verb, including GET methods that change state. A test checks both. Since 1.24.2 (D2) it also lists twelve POST methods Google marks read-only as reads, and Merchant `accounts.dataSources.fetch` as a write (tests/kinds-d2.test.mjs); since 1.26.3, 45 more POST reads and four GET methods that record an event as writes (tests/kinds-destructive.test.mjs). Explain an override in CHANGELOG.md and docs/SECURITY.md, never in its `notes`: a note is appended to the description of every generated tool of that API.
- The destructive rule (since 1.26.3; docs/SECURITY.md "The destructive rule"). A method or tool is destructive (it asks twice, and it asks even under `confirmation: destructive-only`) when it (a) sends a message, invitation or notification to other people, (b) grants or changes sharing, permissions, roles, ownership or admin privilege, (c) disables a security control (2-step verification, SSO, keys), (d) wipes, resets or issues a command to a device, (e) publishes, deploys, commits a release or ends a live session, (f) moves money (refunds, price migrations), (g) replaces or deletes whole content (whole-file replacement, batch edits that can delete content, an update that clears omitted fields, workspace-consuming version creation), (h) permanently destroys key material or held data. Everything else keeps its kind; a plain edit (a one-field patch) is never raised. Generated and gateway methods get it by exact id in config/tool-kinds.json, every binding and version listed (all 275 `setIamPolicy` ids one by one); a new id after a Discovery refresh needs its entry, and tests/kinds-destructive.test.mjs fails for a new `setIamPolicy`. Curated tools get it by `kind`, or per call with `destructiveWhen` (src/core/tools.ts `callKind`: it only raises a write; the tool map keeps `write`, so the hook asks as for a change and the server's form asks as destructive). A method the rule may cover that is not listed keeps its kind until the owner decides; report it. The credential rule wins over a read override: a POST whose name holds a credential word stays a write ("Keyword" holds "key").
- A read never returns a credential (since 1.26.2). A GET or read-named method whose purpose is to return a credential (a secret payload, a key, a token value, backup codes) is a `write` in config/tool-kinds.json, by exact id. A read that returns a credential as one field among others stays a read, and the field is listed in src/core/credential-fields.ts by Discovery schema property; every read result of a per-method tool and of `api_call` is walked along the method's response schema and the field replaced. A write's result is not changed. `api_call` keeps its own name list (SECRET_KEYS in gateway.ts) on every result. tests/credential-reveals.test.mjs walks every snapshot from each read's response schema and scans the catalog by method id; a new credential field or method fails it until it is listed, made a write, or reviewed with a reason there. Gateway-only APIs have no snapshot: their pruned schemas are in tests/fixtures/credential-schemas.json. Hand-written tools strip their own (auth_get_users).
- Every tool lists the four MCP annotation hints (1.24.3): `toolAnnotations` in src/core/tools.ts for the tools of buildTools (readOnlyHint and destructiveHint from the kind; idempotentHint from `ToolDef.idempotent`, else true for a read only; openWorldHint from `ToolDef.openWorld`, else true), and `RUNTIME_TOOL_HINTS` for the runtime tools. A generated tool sets idempotent from the verb (a read, or GET, PUT, DELETE); a curated write sets `idempotent: true` only for one PUT, DELETE or GET method or when the Google tool it matches is marked idempotent. A tool that sends nothing to Google sets `openWorld: false` (api_methods, api_search). A new runtime tool needs an entry in RUNTIME_TOOL_HINTS (runServer throws at start without one). tests/annotations.test.mjs checks every tool of every bundled server. The hints never decide the gate.
- Every server has runtime tools: `health` everywhere, and the sign-in tools (`auth_setup_client`, `auth_login`, `auth_status`, and `auth_setup_admin` for the admin server) where a Google sign-in exists. runServer adds them (src/core/tools.ts, src/core/inchat-login.ts). They must also be listed as reads in the built tool map (dumpTools). A tool missing from the map is treated as destructive by the hook, so every call would ask.
- Several accounts per Google group: a token file per account, listed in accounts.json (src/core/accounts.ts). A tool call names its account with the `account` argument. The wrapper in tools.ts takes it out and sets the account for the handler (src/core/account-context.ts), so it never reaches Google. Clients are made per account by getAuthClient, which caches them per token file. Do not cache a Google client in a server module.
- The token folder is created with ensureTokenDir (src/core/acl.ts), never with a bare mkdirSync: on Windows it limits the folder's access list.
- Secret files (the token files, the client secret and its backups, the API key, the Ads developer token) are read and written only through src/core/secret-files.ts (`readSecretText`, `writeSecretText`, `secretFileExists`, `removeSecretFile`). Never call fs on them directly: the store in use may hold them. The store is chosen by GSM_TOKEN_STORE, then `store.json`, else plain files (mode 0600). `secrets.json` lists the stored names, never content. `gsm protect` / `protect --off` move them (src/cli/protect.ts). A value is read back before its plain copy goes, and a failed run is rolled back. Keep the secret out of argv: the store helpers pass it on stdin (src/core/secret-store.ts).
- The service-account group (gplay, gmerchant) uses a key set up with `setup-service-account` or the chat tool `auth_setup_service_account`. Only the key's path is stored (service-account.json). Its scopes are fixed (SERVICE_ACCOUNT_SCOPES in src/core/auth.ts), and generated since 1.23.1: each product of the group declares `serviceAccountScopes` in config/products.json (`"methods"`: every https scope its methods declare, as requirementsFor counts them; or a list), and `node scripts/gen-service-account-scopes.mjs` (needs a compiled dist/) writes the union to src/core/service-account-scopes.ts, which auth.ts imports. gplay is `"methods"`; gmerchant is `["…/auth/content"]`, so Manufacturer Center (which gmerchant also carries) stays out. Since 1.24.4 each server's token asks for its own product's list only (`SERVICE_ACCOUNT_SCOPES_BY_SERVER`, generated too; `serviceAccountScopesFor(cfg.server)` in auth.ts): runServer puts the server's name into its config (`RuntimeConfig.server`), clients are cached per key file and scope set, and grantedScopes, tokenStatus, the live check, `status --check` (once per server) and `health --check` use the server's list. Without a server (a group-wide command) it is the union. tests/service-account-scopes.test.mjs runs the generator with `--check`. Rerun it when a product of the group changes its APIs. Its tools register only after setup, like the OAuth groups. `GOOGLE_APPLICATION_CREDENTIALS` may hold the key instead.
- gmaps is in the apikey group (its key is apikey.json, shared with gsearch).
- Toolsets (`GSM_TOOLSET`, plugin option `toolset`, src/core/toolset.ts): `all` (default, no filter), `google` (names listed per product in config/products.json `toolsets.google`, with the official Google tool each one `matches`), `curated` (derived from each tool's `origin`: curated and gateway tools). The filter runs once in runServer right after buildTools; the runtime tools are added after it and are never filtered; `dumpTools` (the hook's tool map) stays full. A product without a list falls back to `all` and says so. With `all` the registered list must stay byte-identical: check with an MCP client over every server, unset vs `all`, base vs branch. scripts/gen-servers.mjs validates the lists and copies only the names into config/servers.json; the build fails when a listed tool is not a tool of the server. Both registry loaders (src/core/registry.ts and loadRegistryFile/registryFromProducts in src/cli/products.ts) carry `toolsets`.
- Login scopes follow the toolset (`RequirementOptions.toolset` in src/core/scopes.ts, from `--toolset`, else `GSM_TOOLSET`): only the toolset's tools are requirements, and gateway methods count only when the toolset holds `api_call`. Without a toolset or with `all`, requirementsForSpecs must return the same list as before (snapshot every server against the previous release). The login builds the group's scope universe from every tool, so a narrowed request never makes a usable stored scope look foreign. The chat sign-in adds `--toolset` to the child's argv only when it is not `all`.
- `gsm install --toolset` writes `GSM_TOOLSET` (Codex, OpenCode, agy, through `serverEnvironment` in src/cli/settings.ts) or `--config toolset=<v>` (Claude Code, `configArgs`) only when given; tests/fixtures/adapters-unset-1.2.0.json pins the unset files. agy installs warn when a product can list more than 100 tools (src/cli/toolset-count.ts, counted from tool-map.json). The 100-tool agy cap is UNVERIFIED: `agy mcp list` does not start servers, and a real check needs an agy session (sign-in and a model call). Do not default agy to `google` until it is verified.
- Project readiness: READINESS_GROUPS in src/core/readiness.ts lists the services each login group's products need. Tests check it against config/products.json, so when a product's APIs change, change the list too. The gcloud server exposes `project_readiness` (read) and `project_enable_missing` (write, batches of 20). The consent screen, publishing, test users and the Desktop OAuth client have no API we can use: the readiness output links to the console pages for them.
- Public site: `site/` deploys to GitHub Pages on a push to main that touches `site/**` (`.github/workflows/pages.yml`).
